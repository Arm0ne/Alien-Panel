# 业务逻辑与数据口径

## 1. 业务用户、Inbound 和 Client

业务用户的最小业务边界是“某一台线路机上的某一个用户 Inbound”。Inbound 下的每个 Client/Email 都是同一用户的设备凭证，不会单独生成中央用户。

- 同一 Email 出现在不同 Inbound 或不同节点时，仍是不同业务用户。
- 落地机 Inbound 是基础设施入口，不进入用户管理，也不会自动建用户。
- 用户列表的一行对应一个线路机用户 Inbound。
- `clientCount` 是该 Inbound 的设备数，不是用户数。

## 2. 到期和在线状态

Agent 采集并保存 Inbound 到期字段，但中央业务状态以该 Inbound 下启用 Client 的到期时间为准：

1. 所有启用 Client 到期时间一致，用户使用这个时间。
2. 时间不一致，使用最早的有限到期时间，并记录异常事件，避免用户在某个设备已经到期后仍被视为有效。
3. 没有启用 Client、Inbound 停用或 Inbound 已归档，业务用户显示为停用/异常。
4. 不设宽限期；到期后状态转为已到期，X-Panel 连接能力由本机配置和 Client 状态决定。

财务首笔订单的业务来源是 Agent 同步的线路机用户 Inbound。订单服务开始日期由管理员按实际收费和开通时间填写；服务结束日期使用 Agent 已同步的 Client 派生到期时间，不从当前操作时间重新计算。

## 3. 用户路径和多个出口 IP

当前日常路径存储在 `user_paths`，旧的 `routes/user_routes/route_exit_ips` 仅保留历史和兼容 API：

| 模式 | 允许的出口资产 | 必填条件 |
|---|---|---|
| `relay` | 用户主 Inbound 所属线路机的节点出口 | 不选择落地机 |
| `landing` | 所选落地机的节点出口 | 落地机和基础设施 Inbound 都必须启用 |
| `external` | 独立 S5 出口 | 不能混用落地机 |

一个用户路径可以按顺序选择多个同一模式的出口 IP。后端新增 `user_path_exit_ips` 关联表保存顺序；`user_paths.exit_ip_id` 保留为第一项，用于兼容历史 API 和旧客户端。接口同时返回：

- `exitIpIds`：有序 ID 数组；
- `exitIps`：带地址、来源、归属节点和启用状态的完整对象数组；
- `exitIpId`、`exitIpAddress`：第一项的旧兼容字段。

选择、读取、用户数统计、删除保护和节点删除都检查完整数组，不能通过把 IP 放在第二项绕过关联保护。

## 4. 节点删除与用户生命周期

删除节点是事务操作：节点、Token、Inbound、Client、同步记录、流量快照、成本、出口 IP、用户路径和旧线路关系会被清理。删除后重新计算受影响用户：

- 只要仍有任何启用的线路机用户 Inbound，或仍有有效路径关联，业务用户保留；
- 没有任何线路机 Inbound 和路径关联的业务用户自动逻辑删除并记录 `user.auto_delete` 审计日志；
- `user_billing_records`、续费候选的业务历史和财务审计记录不删除，只解除已经不存在的节点/Inbound引用。

## 5. 收入、续费和成本

- 本业务是付款开通，不存在先用后付，也不设置宽限期。
- “已确认实收”是所有已确认收费记录的真实收款总额；它按收款记录统计，不由用户月费倒推出收款。
- Agent 只发现 Client 到期时间延长，生成待确认续费候选，不自动记账。
- 管理员确认后生成不可变收费记录；选择“非收费变更”只关闭候选，不产生收入。
- 已有客户可通过历史账单批量导入恢复首购和续费链路；导入前支持预览、重复检查和服务区间重叠检查。没有付款凭证的历史记录先标记为待核实，核验前不计入实收和服务期收入。
- 年费订单的服务区间由订单 `serviceFrom/serviceTo` 决定，财务按实际覆盖天数分摊到月份；不是从确认操作时间重新起算。
- 第一阶段成本只记录真实的节点、IP 和其他成本；不把成本均摊到每个用户。节点管理展示每台线路机承载的有效用户数。
- 成本记录的生效日期定义历史版本；修改金额或备注不回写历史生效区间，生效日期变化应新增记录。
