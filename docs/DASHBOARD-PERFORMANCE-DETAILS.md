# 总览页面性能优化详解

本文说明 Alien-Panel 总览页面近期发布的性能优化，覆盖问题来源、实现方式、首次升级行为、统计口径、安全性和验证情况。文中代码状态对应 GitHub `main` 当前发布包：源码提交 `f65d0142a92965734cd5ba16e4e70b397fb2bc65`，发布包提交 `893d9b02b8de44dee6f77b610a9a2569e3e8bc94`。

## 结论摘要

总览变慢的主要原因不是 Agent 数量本身，而是每次总览请求都需要从持续增长的 `traffic_snapshots` 分钟级历史中计算流量增量。数据越多，7 天、30 天和本月统计所需读取和计算的记录越多；多个页面请求同时遇到缓存过期时，还可能重复做相同的重查询。

本次最重要的改动是新增按 Inbound、UTC 小时保存的派生汇总。历史数据完成后台回填后，7/30 天和本月总览改为读取小时汇总，只对时间范围边缘读取原始快照；今日仍读取原始数据。Agent 后续同步会在同一数据库事务内重算受影响的小时，迟到或顺序异常的快照也不会重复累计。

你已反馈部署后总览“明显快多了”。这是当前生产使用反馈；尚未拿到服务器更新前后的 Network 计时或日志耗时，因此本文不把本机压测数字当作生产环境的实际提速比例。

## 问题是怎样形成的

流量表保存的是 Agent 上报的累计计数快照，而总览需要展示一段时间内的上传和下载增量。对相邻两条快照，系统根据累计值差计算流量；如果计数器被重置、出现很长的数据间隔，也要按原有规则处理。

生产基线采样时，数据库大致包含：

| 项目 | 数量 |
| --- | ---: |
| 流量快照 `traffic_snapshots` | 323,801 行 |
| 同步记录 `sync_runs` | 62,674 行 |
| 用户 | 40 |
| 节点 | 14 |
| 用户 Inbound | 68 |
| Client | 184 |

当时观测到总览短缓存命中约 163 ms，缓存过期后的冷查询约 3.61 秒，其中约 3.60 秒花在服务器查询等待上。旧查询计划包含按快照重复查找历史最大时间的相关子查询和临时排序。随着 Agent 继续上报，原始历史自然还会增长，所以只增加普通索引或延长缓存有效期不足以解决长期增长趋势。

## 改动一：把长期历史压成按小时查询的派生汇总

新增数据库迁移 `025_traffic_hourly_rollups.sql`，创建以下辅助结构：

- `traffic_hourly_rollups`：按 Inbound 和 UTC 小时存放上传/下载增量、样本数、观测秒数、重置次数、间隔标记和最新数据时间。
- `traffic_rollup_state`：记录汇总状态、已处理快照数量和完成时间。
- `traffic_rollup_dirty_buckets`：标记回填期间收到新快照后需要重新计算的小时。

原始 `traffic_snapshots` 不会被删除，也不会被压缩替代。汇总是可以重建的派生数据。外部 Dashboard API 字段、图表数据结构及流量统计范围保持不变。

### 哪些范围读取汇总

| 总览数据 | 当前读取策略 |
| --- | --- |
| 今日 | 原始快照。一天范围较短，保留精细的小时趋势。 |
| 7 天 | 完整 UTC 小时使用小时汇总；起止不完整小时使用原始快照补齐。 |
| 30 天 | 完整 UTC 小时使用小时汇总；时间范围边缘使用原始快照补齐。 |
| 本月总流量卡片 | 汇总完整小时并补齐范围边缘；它只需要总量，不扫描生成长期明细。 |
| 自定义范围 | 不超过 48 小时使用原始数据；更长范围在汇总就绪后使用同一小时汇总路径。 |

小时边界很重要：流量增量归入较新那条快照所在的小时。范围边缘仍经过原始数据计算，避免简单截断小时导致统计少算或重复。

### 汇总记录保留了什么

小时汇总并非只保留总字节数，还保留了计算及展示需要的属性：

- 上传、下载增量及样本数；
- 观测时长，用于覆盖率计算；
- 计数器重置次数，用于趋势重置标记；
- 快照间隔过长的标记；
- 最近一条有效数据时间。

对发生重置的快照，仍沿用原来的规则：使用重置后的当前累计值作为该段增量，并将负增量限制为零。因此小时汇总改变的是读取粒度，不是业务统计口径。

## 改动二：历史回填放在后台分批完成

数据库迁移只负责快速建表，不会在迁移事务里一次性扫描全部历史。中央服务启动后，单独启动后台回填：

1. 每批最多读取 5,000 条快照，并独立提交该批结果。
2. 回填处理期间中央服务仍可启动并响应请求，不需要清空数据库，也不需要重新同步 Agent。
3. 如果回填期间又收到新快照，受影响的小时会被标记为待修复；回填收尾时统一重算。
4. 回填完成前，7/30 天和本月会自动使用原始查询路径；汇总状态变为完成后自动切换。
5. 如果回填中断或失败，原始数据仍在；重启后可以重新构建，未就绪时继续走原始查询路径。

中央日志中的 `traffic rollup backfill progress` 表示正在回填；看到 `traffic hourly rollups ready` 才表示可以确认长期范围已经切到小时汇总。回填尚未完成时，长范围仍可能较慢，这是有意保留的正确性回退路径，不应通过删原始数据来处理。

## 改动三：让后续 Agent 同步持续维护汇总

新快照写入与小时汇总维护处于同一数据库事务中。同步过程会识别新快照影响的小时；如果插入的是迟到数据，也会找到其后的下一条快照，重建相应小时，避免旧增量被重复计算或遗漏。

重建采用“从该小时之前的一条基准快照加上该小时内快照重新计算”的方式，而不是在已有小时总量上盲目累加。相同事务还清除已修复的 dirty 标记，因此快照写入和派生汇总不会出现一边成功、另一边失败的中间状态。

## 改动四：减少一次总览请求内的重复工作

小时汇总前的查询优化也包含在当前发布链中：

- 只读取一次符合总览业务范围的用户 Inbound 元数据，并复用于当前范围、今日统计和用户排行。
- 重写原始快照查询：先筛出有效 Inbound，再读取请求时间范围内的快照，并为每个 Inbound 最多补一条范围开始前的基准快照；不再为范围内每条快照重复跑历史 `MAX()` 查找。
- 今日、所选范围的快照按一次有序扫描计算时，避免为多个展示指标各扫一遍相同宽区间。
- 趋势桶先用映射聚合，再按时间排序，避免数据点增加时使用二次复杂度的插入排序。
- 同一 Dashboard 参数的冷缓存请求共享正在执行的查询；缓存锁只保护缓存读写，不会在持锁期间执行慢 SQL。
- Dashboard 结果保留 20 秒短缓存。它减少重复打开页面的查询，但不是长期历史增长问题的主要解决手段。

## 改动五：减少同步路径和前端图表问题

这次发布链还带有以下辅助改动：

- Agent 合并 Client 流量时预先建立 Email、远端 ID 索引，将每条流量记录逐个扫描 Client 列表改为近似线性处理。
- 服务端清理失效 Client 时把逐条 `DELETE` 改为每批最多 500 个 ID 的批量删除，降低同步期间 SQL 语句数量。
- 用户、节点、财务等 GET 页面请求不再同步触发完整状态刷新；状态维护由后台任务承担，减少页面和同步维护相互等待。
- 图表组件增加 DOM 尚未挂载或尺寸为零时的保护，并在实际渲染时刷新图表选项。这修复了条件渲染时可能读空 DOM、首次图表初始化异常的问题，主要是稳定性修复，不是 7/30 天查询提速的来源。
- Dashboard 专用前端请求超时设为 30 秒，避免该接口仍使用较短的默认客户端超时。它不会让数据库查询本身变快，只是避免客户端过早中断。

## 改动六：索引和数据结构整理

- `022_performance_indexes.sql` 增加同步记录的组合索引，以支持按节点、状态和时间查找同步记录。
- `023_drop_redundant_traffic_index.sql` 删除一条重复的流量索引。表上的 `UNIQUE(inbound_id, collected_at)` 已提供等价索引；删除重复索引不会删数据或取消唯一约束。
- 迁移使用幂等写法，以便已经执行过较早数据库迁移的实例也能安全升级。

这些索引不是小时汇总的替代方案；它们分别降低同步记录查询和冗余索引写放大。

## 统计正确性与安全边界

- Dashboard 响应字段、趋势分桶规则、业务范围（relay 用户 Inbound）、节点和用户排行口径保持兼容。
- 上传、下载累计值下降或明确报告重置时，按既有重置规则处理；负流量不会被算入总量。
- 小时汇总按较新快照的时间归桶；头尾不完整小时由原始快照补齐。
- 原始分钟级快照完整保留；本次没有引入历史保留/清理策略。
- 汇总数据可以重建，回填失败时原始路径仍可服务请求。
- 删除 Inbound 时，小时汇总和 dirty 标记通过外键级联清理。
- `024_client_lifecycle.sql` 也包含在发布包中，扩展 Inbound 的 Client 集合和流量基线字段，配合新版 Agent 识别完整 Client 集合变化。它用于同步生命周期正确性，不是总览提速的主要来源。

## 验证情况

发布前执行并通过：

- 后端 `go test ./...`、`go vet ./...` 和 `go build ./...`；
- Agent `go test ./...`；
- 前端 `pnpm.cmd typecheck`、`pnpm.cmd lint` 和 `pnpm.cmd build`；
- 后端 HTTP API `go test -race -short ./internal/httpapi`；
- 汇总回填重置检测和重复运行幂等性测试；
- 68 个 Inbound、30 天 293,828 条合成分钟快照测试：小时汇总查询约 156 ms，并与原始统计算法结果一致；
- Linux amd64 发布包、发布清单及 SHA-256 校验。

156 ms 是开发环境合成数据压测结果，不等于生产环境耗时。生产更新后的主观反馈是“明显快多了”；如需形成正式前后对比，应再记录浏览器 Network 的 7 天和 30 天请求耗时，或比较中央日志 `dashboard query completed` 的 `duration_ms`、`traffic_ms` 与 `traffic_source` 字段。

## 在生产环境确认汇总已启用

在服务器运行：

```bash
sudo docker compose -p alien-panel -f deploy/docker-compose.yml logs --tail=200 central
```

确认日志出现：

```text
traffic hourly rollups ready
```

查询日志里的 `traffic_source`：

- `raw`：当前请求使用原始快照，例如今日或回填尚未完成；
- `rollup`：请求范围使用小时汇总；
- `raw+rollup`：一次总览同时使用原始今日数据与小时汇总长期范围。

`dashboard query completed` 还会输出当前范围、总耗时、流量查询耗时和趋势点数量。冷请求用于衡量查询优化；缓存命中会直接返回，不应与冷请求混在同一组比较。

## 仍未包含的后续优化

- 不同 Agent 的 heartbeat/sync 错峰及随机时间偏移；
- 原始分钟快照的长期保留策略；
- 事件中心轮询改为只读摘要，打开弹窗时再拉取明细。

这些方向会影响调度、数据保留或前端请求行为，需要基于新的生产观测单独评估。本次发布没有删除旧数据，也没有改变 Agent 上报频率。
